# PDCA閉ループ化 設計書（2026-09-01）

## 背景・解決する問題

現行システムは分析(Check)と生成(Act)が繋がっていない**開ループ**である。

- `generator.build_prompt` が分析結果から使うのは 時間帯/本文長/ツリー有無 の3集計値のみ
- analyzer が計算している当たり投稿（top/top_er）の**本文は週次メールで人に見せて終わり**。生成AIには一度も届かない
- 投稿に「どの型で書いたか」を記録する列が無く、型と実績の紐付けが原理的に不可能
- `shares`（共有）を収集しながらエンゲージ率の分子から除外している

結果として「当たった投稿があっても次の生成に反映されず、外れ投稿が量産される」。

## 決定事項（オーナー確認済み）

| 論点 | 決定 |
|---|---|
| 勝敗の判定指標 | **表示回数（views）**。ノイズ対策として平均でなく**中央値**、型ごと最低サンプル数到達まで確定しない |
| ツリー型/求人情報/保存型 | すべて**仮説としてA/Bにかける**（確定方針にしない） |
| 進め方 | **段階式**（第1段→ラベルを貯めながら第2・3段） |
| 競合投稿の収集 | **半自動**（人がスクショをinboxへ→AIが整形・タグ付け・DB登録）。自動収集はThreads API仕様上不可（他アカのデータ・viewsは取得不能） |
| 学習の主体 | **自社実測のみで配分を決定**。競合お手本は「新型仮説の供給」と「型カードの具体例補強」に限定（求人垂直は競合が少なく、ポジション違いの可能性があるため） |
| 案件情報 | NotebookLM→ローカル同期スクリプト→シート。**社名は同期時にマスク**（generatorは実名を見ない）＋コンプラゲートで二重遮断 |
| 検証軸の追加 | **文字数帯・改行スタイル・フック（1行目）**も検証対象。文字数・改行は本文から機械算出（新規列不要）、フックは`フック型`ラベルで捕捉 |
| お手本DBの鮮度 | **更新型**。型ごと容量上限あり・高views候補で差し替え・模倣5連敗の手本は自動退役（下記「お手本DBの更新ルール」） |

## アーキテクチャ（閉ループ）

```
生成(型ラベル付き) → 投稿 → 収集 → 分析(型別中央値)
  ↑                                      │
  └── 勝ち/負け本文＋型別実測＋次サイクル型配分（コードが決定的に計算） ──┘
```

原則：**配分はPython側で決定的に計算し、AIには「内訳指示」として渡す**。AIに配分判断を委ねない（再現性・説明可能性のため）。

## データ層（非公開シート側・§17b遵守）

| タブ | 変更 | 列 |
|---|---|---|
| `投稿_<acc>` | **3列追加** | `フック型`（数字提示/心の声/逆張り/失敗談/問いかけ/場面描写…）・`内容型`（情報提供/共感/暴露/求人紹介…）・`参照お手本ID`（最も強く模倣した手本を生成AIが1つ自己申告。退役判定の紐付けに使用）。ツリー有無・文字数・改行数は本文/既存列から機械算出（列不要） |
| `お手本DB_<acc>` | **新設** | ID/出典(自アカ or 競合名)/本文/フック型/内容型/**ポジション近接度**(同ポジ・近接・別ポジ)/実測(views or likes)/**状態(active/retired)**/**退役理由**/メモ/収集日 |
| `仮説ログ` | **新設** | 日付/仮説/検証方法/結果/次アクション。週次処理が自動追記＋人が手で書ける |
| `案件_<acc>` | **新設** | 案件ID/職種/勤務地(都道府県まで)/給与/特徴/雇用形態/更新日。**格納時点で社名マスク済み** |
| `プロフィール_<acc>` | **拡充** | Persona(何者か/使命/価値観/ストーリー)・Voice(口調/改行/テンポ)・**判断基準（何を言わないか）** |

エイリアス層（`POSTS_FIELD_ALIASES`方式）で列追加は後方互換にする。

## 生成プロンプト構成（抽象×具体ハイブリッド）

全データを流し込まない。渡す順：

1. Persona＋Voice（プロフィールタブ）
2. 型別配分の指示（コードが実測から計算。例：数字提示5本・心の声3本・逆張り2本・探索枠2本）
3. 採用する型の**勝ちパターンカード**＝型の構成テンプレ＋お手本DBから代表例**3〜7本のみ**
4. **NG例**＝自アカの滑った投稿ワースト3＋ガイドライン（勝ち例だけでなく負け例を対比で見せる）
5. 案件情報（求人紹介型の本数分のみ）
6. → 生成 → 機械コンプラゲート（NGワード＋**実社名パターン**）

別ポジの競合例は「フックと構造のみ参考、声・主張はコピーしない」と明示。

## 配分アルゴリズム（第2段）

- 型ごとに**直近28日窓の表示回数中央値**を算出（平均は1本の大当たりに引きずられるため不使用）
- 最低サンプル数（型ごと15本）未満の型は「データ蓄積中」扱いで探索枠から供給
- **探索枠を常設**（12本中2〜3本。求人垂直は競合が少なく自社データ生成を加速する必要があるため厚め）。勝ち型に100%寄せない（環境変化の検知・過学習防止）
- **副次軸の集計**：文字数帯（`by_length`既存）・改行数帯（`by_linebreaks`新設・0/1-2/3-5/6+）・フック型別の中央値を算出し、勝ち帯を生成指示に含める（例「150字前後・改行3-5・数字提示フックが好調」）
- 配分結果と根拠は`仮説ログ`に自動追記

## 投稿時間の最適化

現行の窓内ランダム配置がそのまま実験装置になる（時刻が自然にばらける＋`by_time`集計は既存）。

1. 外部リサーチ＋自アカ28日実測の時間帯別中央値 → アカごと初期仮説の窓を設定
2. 窓を現行より広めに取り探索
3. 週次レポートに「時間帯別中央値＋推奨窓」を出力し、**月1回`PRESETS`の窓を実測で改訂**（3日ごとの自動改訂はノイズに振り回されるためやらない）

## 案件情報同期（NotebookLM→シート）

- GitHub ActionsからNotebookLMは叩かない（認証がローカル・トークンをSecretsに置くのは脆弱）
- ローカルスクリプト `scripts/sync_deals.py`：NotebookLMから構造化抽出→**社名マスク**→`案件_<acc>`へ書込
- 二重ガード：①同期時マスク（主）②`ガイドライン`タブのNGワードに実社名を登録→機械ゲートが最終遮断（非公開シートなので実名を置ける）
- 実行は案件更新時に手動（cron自動化はローカル常時起動前提のため運用が回ってから判断）
- 前提：`nlm login`での再認証（ブラウザログイン1回・第3段着手前に実施）

## 競合お手本の収集フロー（半自動・確定）

1. keitaがスクショを投下：製造業=`製造業Threads/03_お手本inbox/`／占い=`占いThreads-note事業/05_お手本inbox/`（作成済み）
2. セッションで「inbox処理して」→ AIが本文抽出・型タグ付け・ポジション近接度判定→`お手本DB_<acc>`へ登録→スクショを`処理済み/`へ移動（二重登録防止）
3. 目安：週5〜10本

## お手本DBの更新ルール（容量・差し替え・退役）

DBを「貯めっぱなし」にせず新陳代謝させ、トレンド追随と質を担保する。

- **容量**：型ごとに上限7本（プロンプトに渡すのは3〜7本のため。超過保存はノイズ）
- **差し替え**：上限到達後に新候補が来たら、同一出典種別内で実測比較し最下位と入れ替え
  （自アカ同士=views、競合同士=likes。競合のviewsは取得不能なため**混在比較はしない**）。
  差し替えで外れた手本は削除せず`状態=retired`＋`退役理由=差し替え`（履歴保全・復活可能）
- **退役（模倣5連敗ルール）**：ある手本を`参照お手本ID`とする投稿が**5本公開され、
  5本すべての表示回数がそのアカの直近28日中央値未満**なら`状態=retired`＋`退役理由=模倣5連敗`。
  判定と書き戻しは週次処理が自動実行し、`仮説ログ`に記録する。
  全投稿が最適化済みの時間窓で公開されるため「最適な時間に投稿した前提」は常に満たされる
- 生成プロンプトには`状態=active`の手本のみ渡す

## 段階計画

| 段階 | 内容 | 効果時期 |
|---|---|---|
| **第1段** | 型ラベル2列＋勝ち/負け本文のプロンプト注入＋shares算入＋探索枠／`お手本DB`・`仮説ログ`タブ新設／プロフィール拡充curation | 次サイクルから生成品質が変わる。A/Bの材料が貯まり始める |
| **第2段** | 型別中央値集計→配分自動化／仮説ログ自動追記／時間帯レポート強化＋窓改訂 | ラベル30本超（約2週間後） |
| **第3段** | NotebookLM案件同期＋求人紹介型バリアント投入／ツリー型検証 | 第2段の基盤の上 |

## テスト方針

既存流儀を踏襲（API不要・モック・純関数中心）：配分計算（中央値/最低サンプル/探索枠）・プロンプト組み立て（型カード/NG例の選抜数）・社名マスクは純関数として切り出しユニットテスト。シート列追加はエイリアス層のテストで後方互換を担保。

## §17（公開repo）遵守

エンジンコード・本設計書=公開OK。型の実測値・お手本DB・案件情報・社名リスト・プロフィール=非公開シートのみ。inboxフォルダはローカル（repo外）。
