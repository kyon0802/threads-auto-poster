## 先行設計との関係（2026-09-09 追記・重要）

本設計は、先行する **2026-09-06「横断分析基盤」設計の③を、置き場所を変えて縮小実装したもの**。
実装時に先行設計を確認しておらず、別途オーナーと相談して置き場所を決めたため方針が分かれた。
オーナー判断（2026-09-09）により、**本実装を第1段として残し、先行設計側に現状を追記して整合**させた。

- 一致：投稿しない／生成しない／在庫監視の対象外／投稿タブを作らない／本文を保存／**中央値を主指標**
- 相違：置き場所が「分析専用の別シート」ではなく「既存 seizogyo シートに相乗り」
- 未実装として残るもの（自社との横断比較・横断ダッシュボード・お手本DBへの還元）は先行設計に記載

## 背景

自社4アカウント（takumi / 住田 / ぱし / 澪）に加えて、**外注先が運用する2アカウント**を
システムに載せる。ただし用途が根本的に違う。

| | 自社4アカ | 外注2アカ |
|---|---|---|
| 投稿を書くのは | こちら（AI生成＋人の確認） | 外注先 |
| システムの役割 | 投稿の生成と公開 | **実績の収集と、外注の作業量の監督** |

外注アカを自社アカと同じ扱いにすると、次の事故が起きる。

1. **外注先のアカウントに勝手に投稿してしまう**（最も重大）
2. AI生成が走る → 誰も公開しない投稿にAPI課金だけ発生し、外注先の投稿とも二重になる
3. 在庫監視が毎日 critical → Actions が赤く固定され、**本物の停止を見逃す**（§10・CHANGELOG §27 の再来）

この3つを機械（テスト）で禁止するのが本設計の主目的。

## 決定事項

- **置き場所**: 既存の seizogyo シートに相乗り（同じ製造業求人で比較しやすいため）。
  → よってフラグは**事業単位ではなくアカウント単位**になる。
- **区別の方法**: `accounts` タブに「運用種別」列を追加。空＝自社、「外注」＝外注アカ。
  GitHub Variable での列挙は採らない（シートとVariableの2か所を見ないと分からずズレる）。
- **成果物**: 週次レポートに外注の作業量を出す。AIによる改善指示の自動生成や自社との比較は今回やらない（YAGNI）。

## 入口ごとの挙動

| 入口 | 自社 | 外注 | 理由 |
|---|---|---|---|
| `post.yml` 投稿 | する | **しない** | 外注先のアカウントへの誤投稿は重大事故 |
| `post.yml` トークン更新 | する | **する** | 60日で失効すると収集が止まる |
| `collect.yml` 収集 | する | **する** | これが主目的 |
| `weekly.yml` AI生成 | する | **しない** | 公開されない投稿への課金＋二重投稿 |
| `weekly.yml` レポート | 従来の週次レポート | **外注作業量レポート**（2アカを1通に） | 見たい問いが違う |
| `monitor.yml` 在庫監視 | する | **しない** | 投稿しない＝在庫は常にゼロ |

### 未知の運用種別は「自社」扱い

打ち間違い（例「がいちゅう」）は自社扱いにする。外注扱いに倒すと自社アカの投稿が全停止するが、
逆は実害が小さい（外注アカには投稿タブ `投稿_<acc>` を作らない運用なので公開対象の行が存在しない）。
被害の小さい側を既定にし、publisher が警告ログで人に気づかせる。

## 本文の保存

使い回し率は本文の照合でしか出せない。調べたところ **Threads API の投稿一覧は元から本文を返しており**
（`threads_api.list_media` の fields に `text` あり）、`collector.py` が本文長だけ保存して本文を捨てていた。
`インサイト_<acc>` に「本文」列を1つ足すだけで済む。**API 呼び出しは増えない。**

## 外注管理指標（`threads_poster/vendor.py`）

`analyzer.py`（＝自社の勝ちパターン抽出）とは分ける。見たい問いが違うため。

2026-09-08 の実測分析（外注2アカ・33日・151投稿）で実際に判断材料になったものだけを採る:

- **新しく書いた本文の数**（＝実際の制作量。投稿本数とは別物。実測では151本中91本）
- **使い回し率**（実測40%。直近週は78%）
- 稼働日数 / 無投稿日
- 投稿の多い時間帯
- **表示の中央値（主指標）**・平均（併記）・合計・表示5以下の本数

### 表示は中央値を主指標にする（先行設計の必須要件）

2026-09-06 設計より：「連携直後に委託先アカウントの1ヶ月分を実測したところ、**平均表示と中央値表示で
評価が逆転する**ケースが実際に出た。1本の突出した投稿が平均を押し上げ、残り半数が表示ひと桁という分布」。
平均だけで判断すると外注先への指示が逆になるため、レポートでも中央値を先に出し、平均は乖離を
見せるための併記に留める。

本文の照合は「空白を除いた完全一致」。類似判定は誤検知が怖いので採らない。

### 集計上の落とし穴（テストで固定）

- **日次スナップショットの重複**: インサイトは `posted_id × 取得日` で毎日1行積まれる。素直に数えると
  1本の投稿が日数ぶんに膨らみ作業量を過大評価する → 投稿単位に畳んで最新スナップショットを採用。
- **本文が空の行**: 本文列を足す前に収集された行は本文が空。これを重複と数えると使い回し率が100%に
  見える → 集計から外し、`text_missing` として件数を明示する。

## 人がやること（コードでは代われない）

### まず既存トークンを確認する（取り直す前に）

長期トークンは**60日有効**。2026-09-07 に発行していれば 11月上旬まで生きている。
どのシートに登録済みか・まだ使えるかを、読み取り専用で確認できる:

```
python3 scripts/check_accounts.py --sheet-id <ID> --verify
```

トークンの値は表示せず、「あるか／いつ更新したか／実際に使えるか」だけを出す。
**生きていれば認可からやり直す必要はない**（下の「登録だけ」へ）。

| 確認結果 | やること |
|---|---|
| 登録済み・使える | 何もしなくてよい（運用種別が `外注` かだけ確認） |
| 手元にトークンがある（未登録） | 列追加 → **登録だけ**（手順B） |
| 失効・行方不明 | 認可から取り直す（手順C） |

### 手順A：列の追加（どの道これは必要・1回だけ）

```
python3 scripts/add_vendor_columns.py --sheet-id <ID>          # 確認のみ
python3 scripts/add_vendor_columns.py --sheet-id <ID> --apply  # 実行
```

### 手順B：既存トークンを登録するだけ

```
python3 scripts/setup_account.py --token-file <トークンを書いたファイル> \
    --account <アカウント名> --role 外注 --sheet-id <ID>
```

**投稿権限つきのトークンでも問題ない**（下記）。`--add-test-post` は付けない（スクリプトが拒否する）。

### 手順C：取り直す場合だけ

1. 外注先に **Threadsテスター追加 → 承認**をしてもらう（アカウント所有者しかできない）
2. `python3 scripts/get_auth_url.py --collect-only` → 対象アカでログインした状態で承認
3. `python3 scripts/exchange_token.py <認可コード> --out ~/.config/threads-poster/vendor_a.tmp`
4. 手順B で登録 → 終わったらトークンファイルを `rm`

### 投稿権限つきトークンをそのまま使ってよい（2026-09-11 判断）

先行設計には「分析専用アカウントのトークンに投稿権限を付与しない」とあるが、
これは**必須ではなく多層防御の1枚目**。既に発行済みのトークンを使い回せるほうが運用が軽い。

- **投稿を止めているのはコード側**（`publisher` が運用種別=外注をスキップ・テストで固定）。
  さらに外注アカには投稿タブ `投稿_<acc>` を作らないので、そもそも公開対象の行が存在しない。
- 収集に必要な権限は投稿権限つきトークンにも含まれるため、**そのまま収集できる**。
- `--collect-only` は**新規取得するときの推奨**として残す（コストがゼロなので、取り直すなら付ける）。

つまり「2種類のトークンを発行し分ける」必要はない。**取り直すときだけ権限を絞る**。

| | 自社アカ | 外注アカ（新規取得時の推奨） | 外注アカ（既存を流用） |
|---|---|---|---|
| threads_basic | ○ | ○ | ○ |
| threads_manage_insights | ○ | ○ | ○ |
| threads_content_publish | ○ | ×（`--collect-only`） | ○のままでよい |

`setup_account.py` は運用種別の打ち間違い（例「がいちゅう」）と、外注アカへの
`--add-test-post` を**登録の入口で拒否**する。前者は `is_outsourced()` が未知値を自社扱いに
倒す設計のため、入口で止めないと「外注のつもりが自社で登録」される。
