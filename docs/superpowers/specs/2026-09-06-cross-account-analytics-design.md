# 横断分析基盤（分析専用アカウントの取り込み）設計

- 状態: 設計合意済み（実装計画はこれから）
- 関連: [2026-09-01-pdca-closed-loop-design.md](2026-09-01-pdca-closed-loop-design.md) / CLAUDE.md §17

## 1. 目的と背景

自社4アカウントは「投稿 → 収集 → 分析 → 生成」の閉ループで回っている。
一方、**運用を外部に委託しているアカウント**が別に存在し、こちらは
**投稿はシステムの管轄外**（委託先が手動で投稿する）だが、**実績データは自動で取りたい**。

現状これらは分析対象に入っていないため、次のことができない。

1. 委託先の成果を数字で評価する（稼働量・地力・打率を分けて見る）
2. 委託先アカウントで当たった投稿の型を抽出し、自社アカウントの知識源に還元する
3. 自社と委託先を横断して「どのアカウントが伸びているか」を1枚で比較する

### 初回実測で分かったこと（設計判断の根拠）

連携直後に委託先アカウントの1ヶ月分を実測したところ、
**平均表示と中央値表示で評価が逆転する**ケースが実際に出た。
1本の突出した投稿が平均を押し上げ、残り半数が表示ひと桁という分布である。

このため本設計では **中央値を主指標**とし、平均は「乖離を見せるための補助」として併記する。
平均だけで判断すると委託先への指示が逆になるため、これは必須要件である。

## 2. スコープ

### やること

- 分析専用アカウントのインサイト日次収集（既存 collector を流用）
- 投稿本文の保存（勝ちパターン抽出のため）
- 自社＋委託先を横断した集計（当たり判定・アカウント比較・時間帯）
- 横断サマリシート（1スプレッドシート）＋ HTMLダッシュボード
- PDCAサイクルの曜日固定化（生成 週2回／レポート 週1回）
- トークン自動リフレッシュの担当ジョブ移設

### やらないこと（明示的に対象外）

- 分析専用アカウントへの自動投稿（トークンに投稿権限を付与しない）
- 分析専用アカウントの在庫監視（投稿しないので在庫の概念がない）
- 既存 `threads_poster/` の投稿ロジックの変更（トークン共通化の1点を除く）
- 委託先アカウントの投稿タブ作成（作らない＝publisher の対象になり得ない）

## 4. 分離設計（最重要要件）

アカウント数が増えても投稿システムと混ざらないことを、**3層で担保**する。

### 4-1. 設定の分離（主たる防御）

分析専用シートのIDは `BUSINESSES` に**入れない**。
投稿系3ジョブ（post / weekly / monitor）は `resolve_business_sheets()` を通るため、
分析専用シートのIDを一度も受け取らない。設定ミスでも投稿対象になり得ない。

`resolve_business_sheets()` は変更しない。
`resolve_analytics_sheets()` を `threads_analytics/sources.py` に**別関数として追加**する
（既存4ジョブの挙動を1バイトも変えないため）。

### 4-2. 権限の分離（APIレベル）

分析専用アカウントのトークンは、
**`threads_basic` + `threads_manage_insights` のみ**で取得する
（`threads_content_publish` を要求しない）。
仮に設定を誤って投稿対象に入れても、Threads API 側が投稿を拒否する。

- 取得時に、コンテナ作成を1回試して**投稿権限が無いことを実測確認**する運用とする
- 将来これらのアカウントで自動投稿したくなった場合は、権限を付け直して再認可する

### 4-3. 機械保証（テスト＋起動時チェック）

- `ANALYTICS_SHEETS` のIDが `resolve_business_sheets()` の戻り値に**絶対に現れない**ことをテストで固定
- 両Secretに同じIDが入っていたら**起動時にエラーで落とす**（設定ミスの早期検知）
- `collect` / `cross` は両方を読み、**重複なくマージ**する

## 5. データモデル

### 5-1. 投稿本文タブ `投稿本文_<acc>`（新規）

インサイトタブは `(posted_id, 取得日)` 単位＝**投稿1本につき毎日1行**が積まれる。
ここに本文を持たせると同じ文章が何十回も複製され、行数・セル量が実用限界に近づく。

そこで本文は **`posted_id` 単位で1本1行**の別タブに持つ。

| 投稿後ID | 投稿日時 | 本文 | メディア種類 | permalink | 初回取得日 |
|---|---|---|---|---|---|

- 収集時、**未登録の posted_id だけ追記**（既存行は触らない＝書込も増えない）
- インサイトタブは数値のみのまま。横断分析時に `posted_id` で結合する
- 自社4アカにも同じタブができるため、**自社の過去投稿も本文つきで分析可能**になる

`collector.py` の変更点は「`list_media()` が既に返している `text` を新タブへ流す」1箇所のみ。

### 5-2. 横断サマリシート（新規スプレッドシート・Secret `CROSS_SHEET_ID`）

事業シートを跨ぐため、専用に1枚用意する。書き込みは**毎回全置換**
（履歴は各事業シートのインサイトタブが持つ。サマリは常に最新のみ）。

**タブ1 `アカウント比較`** … これだけ見れば状況が分かる主画面

| 事業 | アカウント | 区分 | 投稿数(7日) | 中央値表示 | 平均表示 | ER中央値 | 当たり本数 | 当たり率 | フォロワー | 増減(7日) | 中央値の前週比 |
|---|---|---|---|---|---|---|---|---|---|---|---|

- **集計窓**：この表の数値はすべて**直近7日**（`当たり`判定の基準となる中央値だけは直近28日＝§6-1）
- `区分` は**どちらのSecret由来のシートかで機械的に決める**
  （`BUSINESSES` → 自社／`ANALYTICS_SHEETS` → 委託）。人が入力する列は作らない
- `中央値の前週比` は「直近7日の中央値表示 ÷ その前7日の中央値表示」。
  前7日が0本または中央値0なら `-`（ゼロ除算と無意味な倍率を避ける）
- **中央値と平均を必ず並べて置く**（乖離が一目で分かるため。§1の実測根拠）

**タブ2 `当たり投稿`** … 全アカ横断・倍率2.0以上を降順

`順位 / アカウント / 投稿日時 / 曜日 / 時間帯 / 倍率 / 表示 / いいね / 返信 / ER / 本文 / リンク`

**タブ3 `滑り投稿`** … 倍率0.5以下（同じ列構成）。「やってはいけない型」の教材

**タブ4 `時間帯別`** … `アカウント / 時間帯 / 本数 / 中央値表示 / 参考値フラグ`

## 6. 分析ロジック（`crossview.py`・純関数）

### 6-1. 当たり／滑りの判定

アカウントごとに地力（フォロワー数・配信のされ方）が違うため、絶対値では比較できない。
各投稿を**そのアカウント自身の平常値**と比べる。

```
倍率 = その投稿の表示回数 ÷ そのアカウントの直近28日の表示回数の中央値

当たり: 倍率 >= 2.0
普通  : 0.5 < 倍率 < 2.0
滑り  : 倍率 <= 0.5
```

- **平均ではなく中央値**を基準にする（1本のバズで基準が壊れ、以後すべてが「滑り」に見えるため）
- **投稿から48時間未満は判定対象外**（表示が伸びきる前に「滑り」と誤判定するため。
  PDCA閉ループ設計と同じ扱い）
- 表示回数が0または欠落の行は判定対象外
- しきい値（2.0 / 0.5）は定数として1箇所に置き、運用しながら調整可能にする

### 6-2. アカウント評価の指標

総表示回数だけで並べると投稿本数が多いアカウントが自動的に1位になり、
委託先の評価にならない。次の5指標を分けて出す。

| 指標 | 読み取れること |
|---|---|
| 投稿本数（7日） | 委託先の稼働量（サボり検知） |
| 表示回数の中央値 | 1本あたりの地力（本数に左右されない） |
| ER中央値 | 見られた後の刺さり方 |
| 当たり率（当たり本数 ÷ 投稿本数） | 打率。安定して当てているか |
| フォロワー増（7日） | 最終成果 |

「本数は多いが中央値が低い」＝量産して滑っている、
「本数は少ないが当たり率が高い」＝丁寧だが供給不足、のように指示が分かれる。

### 6-3. 時間帯分析の制約（誤読防止）

**自社アカウントの数字は時間帯の比較に使えない。**
`schedule.PRESETS` で決められた窓にしか投稿していないため、
「その窓が良い」のか「その窓しか試していない」のか区別できない。

- 委託先アカウント（自由投稿）＝素直に比較してよい
- 自社アカウント＝窓の中での比較のみ。ダッシュボードに**制約を明記**する
- **サンプル5本未満の時間帯は「参考値」としてグレー表示**（偶然を実力と読み違えないため）

**時間帯の刻み**：JSTの**1時間単位（0〜23時）**で `投稿日時` からビン分けする。
集計値は各ビンの**中央値表示**（平均は外れ値に引きずられるため使わない）。
集計窓は直近28日（7日だとビンあたりの本数が足りず、ほぼ全ビンが参考値になるため）。

## 8. サイクルの曜日固定（生成 週2回／レポート 週1回）

現在は `is_cycle_day`（起点からの3日周期）1つで生成もレポートも同じ日に走り、
**曜日が毎週ずれる**。これを2つのゲートに分ける。

```
is_cycle_day(today)   → today.weekday() in {日, 水}   … 分析 → 生成
is_report_day(today)  → today.weekday() == 日         … 分析 → レポート → メール
```

- どちらでもない日は即終了（現状と同じ）
- 両方に当たる日曜は `分析 → 生成 → レポート → メール` の順
  （生成結果をレポートに載せる既存の設計意図を維持する）
- 頻度は実質いまと同じ（3日周期 ≒ 週2.33回 → 週2回）。AI呼び出し回数・費用はほぼ変わらない

### 8-1. 生成本数が固定から可変になる

| 生成日 | 埋める範囲 | 本数（4本/日） |
|---|---|---|
| 日曜 | 月・火・水（3日） | 12本 |
| 水曜 | 木・金・土・日（4日） | 16本 |

**生成本数は「次のサイクル日までの日数 × POSTS_PER_DAY」で自動計算**する。

### 8-2. ★移行時の事故ポイント

Variable `GEN_POSTS_<NAME>` に **`12` が固定で入っている事業がある**。
このままだと4日区間でも12本しか作られず、**毎週1日分（4本）の穴**が空く。

- `GEN_POSTS_<NAME>` の用途を **「0 = その事業だけ生成オフ」に限定**する
  （1以上での本数上書きは後方互換として残すが、運用では使わない）
- 移行手順として **Variable に入っている `12` を削除**する。手順は CLAUDE.md に明記する
- 消し忘れても `monitor.yml` の在庫警告が拾う（二重の安全網）

### 8-3. 分割生成

16本を1回のAI呼び出しで作ると型のバリエーションが痩せる。
**1回あたり最大8本に分割**して生成する（12本→6+6、16本→8+8）。

## 9. トークン自動リフレッシュの移設

分析専用シートを `BUSINESSES` から外すと、
リフレッシュを担当していた publisher が触らなくなり、**60日でトークンが失効する**。

- publisher 内のリフレッシュ処理を **`threads_poster/tokens.py` の共通関数として切り出す**
- publisher と collector の両方から呼ぶ
- collect は `BUSINESSES` + `ANALYTICS_SHEETS` を見るため、分析専用アカも毎日リフレッシュされる

同じロジックを2箇所に複製すると、片方だけ直して失効事故を起こす。
共通化を選ぶ。publisher に手を入れる唯一の箇所であり、
**挙動を変えない切り出し**なので既存テストが等価性の安全網になる。

## 10-2. 実装の順序（3段階・各段で単独リリース可能）

本設計は独立した3つの塊からなる。まとめて実装せず、この順で進める。

| 段 | 内容 | なぜこの順か |
|---|---|---|
| ① | **サイクルの曜日固定**（§8） | 分析基盤と無関係に独立。小さく、いま Variable `12` の穴を抱えているので先に閉じる |
| ② | **トークンリフレッシュの共通化**（§9） | ③の前提。単独では挙動が変わらないため、既存テストで安全性を確認しやすい |
| ③ | **横断分析基盤**（§3〜§7） | ①②の完了後。新パッケージ・新ワークフロー・シート追加を含む最大の塊 |

触れるファイルは段ごとにほぼ分かれている
（① `main_weekly.py` / `generator.py`、② `publisher.py` / `collector.py` / 新 `tokens.py`、
③ `collector.py` / `sheets.py` / 新パッケージ）。
**②と③だけが `collector.py` で重なる**ため、この2つは並行させず順に進める。

## 11. 移行手順（運用・順序を守る）

1. 分析専用の新規スプレッドシートを作成し、サービスアカウントに共有
2. `accounts` タブを作成し、取得済みトークンを登録（**投稿タブは作らない**）
3. Secret `ANALYTICS_SHEETS` を追加（`BUSINESSES` は変更しない）
4. Secret `CROSS_SHEET_ID` を追加（横断サマリ用の新規スプレッドシート）
5. コード変更をマージ（テスト全通過を確認）
6. `cross.yml` を**手動実行**して、横断サマリとダッシュボードの出力を目視確認
7. **Variable `GEN_POSTS_<NAME>` の `12` を削除**（8-2）
8. 次のサイクル曜日（日曜）から新スケジュールで稼働することを `monitor.yml` で確認
